# Does this code fit the repo?

Pasted code is often written against a *different* version of the project than
the one on disk: a refactor the author is planning, an architecture another
tool invented, or a layout from three commits ago. It reads as perfectly good
code, which is exactly why it slips through.

The failure is quiet. The file lands, the commit succeeds, and the app breaks
somewhere else entirely — or worse, the code is simply inert and nobody notices
for a week.

This check takes about a minute and answers one question: **if I put this file
at that path, does everything that touches it still work?**

## The check

### 1. Find every file that depends on the target

```bash
# Who imports it?
rg -n "from ['\"].*<basename>" --glob '*.{js,ts,jsx,tsx,mjs}'
# Who constructs or calls the thing it exports?
rg -n "new <ExportName>|<ExportName>\." --glob '*.{js,ts,jsx,tsx,mjs}'
```

If nothing imports it, the file is either an entry point or orphaned — worth
knowing before you publish, because an orphaned file that nobody loads will
never show its effects no matter how correct it is.

### 2. Compare the contract, not the contents

For each dependency found, line up what the callers expect against what the new
file provides:

| Check | What to compare |
| --- | --- |
| **Exported names** | Does it still export everything importers destructure? A file that drops `export const BUILDINGS` breaks every `import { BUILDINGS }`. |
| **Constructor arity** | `new Renderer(game)` versus `new Renderer(canvas, minimap, game)` — a mismatch silently binds the wrong object and fails later with a confusing error. |
| **Method names** | Callers invoking `.render()` on a class that now defines `.draw()` throw on the first frame. |
| **Object shape** | The new code reads `game.map.tiles[y][x]`; does the repo's map expose `.tiles`, or is it a flat typed array? |
| **Units and coordinates** | Positions in tiles versus pixels is the classic silent corruption — nothing throws, everything renders in the wrong place. |
| **Constants duplicated elsewhere** | Prices, sizes and limits repeated in markup or config drift out of sync with the module that enforces them. |

### 3. Report before you overwrite

State the verdict in one line, then the specifics. Concrete beats vague:

> **Does not fit.** This exports `Renderer` with `constructor(game)` and a
> `draw()` method, but `main.js` calls `new Renderer(canvas, minimapCanvas,
> game)` and `renderer.render()`, and `input.js` calls `renderer.screenToWorld()`
> and `renderer.centerOn()`, neither of which this version defines. Dropped in
> as-is, the page fails at load with `renderer.centerOn is not a function`.

Then give the options rather than picking unilaterally, because the author may
be mid-refactor and know exactly what they are doing:

1. **Write the missing glue** — build the host or adapter the new code expects.
   Right when the pasted file is the direction the project is heading.
2. **Adapt the incoming code** to the existing contract. Right when the repo's
   architecture is settled and the paste is a one-off.
3. **Publish it somewhere harmless** — a second entry point or a branch — so
   nothing that currently works breaks while the direction is decided.

## Proving it rather than guessing

When the stakes justify a minute more, don't argue from reading — demonstrate.
Copy the repo to a scratch directory, drop the file in, and load it:

```bash
cp -r <repo> /tmp/fitcheck && cp <incoming> /tmp/fitcheck/<path>
# then load the entry point and capture the actual error
```

An error message quoted from a real run ends the discussion in a way that
"I think this might not match" never does. It also protects you from the
opposite mistake: refusing to publish something that would have worked fine.

## When to skip

Not everything needs this. A new file nothing imports yet, a README, a CSS
tweak, or an asset can go straight in. Reserve the check for modules other code
depends on — that is where the silent breakage lives.
